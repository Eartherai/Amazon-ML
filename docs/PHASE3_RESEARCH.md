# Phase 3 research: retrieval before model complexity

Research checked 2026-09-25 against primary papers, author repositories, official documentation and model cards. This is a bounded research sprint, not an assertion that every paper was reproduced. No competition records were searched externally; no external datasets, weights or benchmark labels were imported. No paid resources or model training were used for this research.

## Decision from our evidence

The current full-target pilot recovers 2,667/3,449 positive links (77.33%) across 1,000 development S1 queries. Its 0.86630 oracle macro F0.5 is an upper bound for that candidate set, not a classifier score. Improving this ceiling matters more than changing a matcher that cannot see missing pairs. The pilot is balanced US/India, not population weighted; France is unlabeled. Research priorities below are engineering judgments informed by Phase 2, not measured gains.

Our highest-value signals are corrupted tokens, cross-script variation, common-name collisions, independently informative addresses and irreversible losses from overly tight retrieval caps. Keep raw, Unicode-preserving light, Latin-folded and transliterated views independent. Phase 2 found 536/1,000 queries without eligible rare-name keys and 47/50 true singletons with candidates. Candidate existence is therefore not a singleton classifier. Postal or house-number disagreement cannot be an unconditional exclusion rule.

## Small multilingual embedding candidates: exact revisions checked

Read-only Hugging Face model API, pinned model cards and configuration files were inspected on 2026-09-25. No model weights were downloaded. Both selected repositories report 117,653,760 floating-point parameter elements; the safetensors total additionally counts 512 integer buffer elements. Both are well below 8B and use a 384-dimensional hidden representation. Their advertised sentence retrieval quality does not establish entity identity matching accuracy.

These are candidates eligible for further implementation review based on inspected model-card declarations, not a complete dependency/legal audit or a claim the entire pretrained corpus is known. Pin revisions and record actual weight hashes when downloading. Neither generic multilingual model justifies introducing external business facts.

[FAISS](https://github.com/facebookresearch/faiss) is MIT-licensed. Its [official index documentation](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes) distinguishes exact Flat, HNSW, IVF and quantized indexes. For 10,320,219 targets and 384 dimensions, raw float32 vectors alone occupy **14.76 GiB**, float16 **7.38 GiB**, and 8-bit codes **3.69 GiB**, excluding IDs, models, graph/list structures, buffers and copies. A flat vector index therefore competes with almost all usable Mac memory. A 48-byte PQ code plus an 8-byte ID is roughly **0.538 GiB**, but quantization and IVF introduce extra recall loss that must be measured against exact vector search on a bounded test. These are arithmetic estimates, not measured memory or quality. Name and address separate indexes multiply storage. CPU FAISS does not imply Apple's GPU accelerates FAISS.

## Ranked retrieval experiments

All priorities use the same held-out S1 queries against the full realistic target pool. Increase query coverage after the first implementation check; do not choose final settings from just 1,000 entities. Preserve closed fold 4 for a later one-time evaluation. Fit IDF/vocabulary/codebooks on training-permitted records; indexing held-out targets for inference is distinct from fitting parameters on them.

1. **Character 3/4/5gram name routes**, light and Latin-folded views, top-K at 20/50/100/200. Start with an exact memory-bounded or inverted-index implementation; measure marginal recall beyond the current union. Add 2grams as a rescue ablation, since their larger common posting lists can overwhelm short-name ranking.
2. **Address-only character route plus independent field fusion.** Missing address must fall back to names. Keep numeric agreement/disagreement as ranking features, not filters. Compare separate fields against concatenation so long addresses do not bury the name.
3. **Transliterated sparse routes.** Cache generic local transliteration, version the backend, compare raw-script + Latin union. Especially relevant to the observed Indian cross-script error slice. Quantify added false-candidate volume and recovery; transliteration alone is not matching evidence.
4. **BM25 word/character inverted retrieval and selective rare-token relaxation.** Compare score variants and caps using the same targets. Fanout-aware retrieval should fall back rather than dropping all queries without rare keys. Record IDF-fit provenance; standard search engines may recompute corpus statistics over the index and violate our train-only fitting policy if silently adopted.
5. **Reciprocal retrieval / reverse top-K into S1.** Indexing 2.21M S1 can lower index memory. Union reverse candidates with forward candidates; never treat a target's nearest S1 as a forced match. Evaluate 1/5/10 reverse neighbors and ownership-conflict rates. This is a retrieval hypothesis supported by structure, not a final assignment rule.
6. **Adaptive union budget.** Retain per-route provenance and inspect positives lost at route cap, fusion and final cap. Use wider budgets for low-confidence/no-address/cross-script queries only after development evidence. Avoid a confidence rule that starves precisely the hard queries.
7. **MinHash/LSH or prefix-filter similarity join**, bounded subset initially; compare unique recovered positives per million added candidates. A shared-prefix heuristic is not an exact prefix-filter join; specify which one is implemented and any completeness guarantee.
8. **Small multilingual dense rescue**, then supervised contrastive adaptation if it finds truly complementary links. Start with a representative subset but evaluate promising configurations against full distractors before accepting recall. Compare dense ANN loss separately from representation failure. Only scale after a runtime/memory/spend estimate and shutdown path.

The first model should be a lexical LightGBM matcher trained on representative retrieved candidates and hard negatives, with raw/normalized number and name/address disagreements. Hold out entities and their owned targets from fitting. Select thresholds on entity-level macro F0.5, with singleton and non-singleton slices and country robustness; candidate recall is a gate, not the final objective. A no-match candidate set cannot prove singleton status. A high-recall candidate union can still have low precision until the matcher learns to reject it.

## Measurement protocol and stopping rules

For each route and union, retain candidate pairs and route/rank/score provenance; report full pool size, query sampling, fit corpus, total pairs, candidate recall by country/source/script/match count, zero-candidate fraction, complete-entity recovery, per-entity mean recall, oracle macro F0.5, candidate-count p50/p95/p99, wall time, peak RSS, disk and extrapolation method. Bootstrap uncertainty by S1 entity, not by pair. Report macro averages separately from link-weighted recall.

Add a route only if it materially improves missing-link/low-ceiling slices for its added compute and candidate cost. Never quietly call reduced-pool retrieval a full-target benchmark. Repeated full scans may be appropriate for a 1,000-query correctness probe but do not imply feasible 1.73M-query inference; build a reusable index before extrapolating. Do not spend on GPUs until a measured sample supports incremental gains and the total record/pair inference cost is budgeted. Preserve disk reserve and avoid duplicating all float vectors or posting lists in Python objects.

The provided metric example has two true positives and one false positive: `F0.5 = 2.5 / 3.5 = 0.7142857`. More generally `F0.5 = 1.25 TP / (1.25 TP + FP + 0.25 FN)`. Thus the denominator gives an FP four times the coefficient of an FN; describing beta=0.5 as a literal “2× penalty” is imprecise. Per-entity macro averaging and empty/empty=1 are authoritative. No threshold should be optimized on pairwise F1 or an assumed fixed cost ratio alone.
